An AI chat you run yourself, on whichever model you like.

A full chat application — streaming replies, documents, code and spreadsheet artifacts, accounts, history — with every conversation stored in your own PostgreSQL database, on your own box.

The model vendor is a line of configuration, not a dependency. Set ANTHROPIC_API_KEY and you are on Anthropic; set GROQ_API_KEY and you are on Groq; point OPENAI_COMPATIBLE_BASE_URL at Ollama or vLLM and nothing leaves your machine at all. Set several and switch between them in the model picker.

It is a fork of Vercel's AI Chatbot template, and it says so on the front page rather than in a footnote.

Live demo — bring your own key

A real chat, running entirely in this page. There is no backend here: your browser talks straight to the provider you choose. It exists to make one point concrete — the model provider is a setting, not a dependency.

Read this before you paste a key

  • This page has no server. It is a static file on GitHub Pages. There is nowhere for it to send your key.
  • Your key is stored in this browser only, in localStorage, and only if you tick the box below. Use the Forget key button to delete it.
  • Requests go directly from your browser to the provider's own API. No proxy, no relay, no key belonging to anyone else.
  • You are spending your own quota. Every message is billed to your account with that provider.
  • A key pasted into any web page is a key you should be able to revoke. Use a scoped or disposable key if your provider offers one.

Which providers a browser can actually call

Calling an AI API directly from a web page is not a matter of taste — it is a matter of whether the provider returns CORS headers. These results were obtained by sending a real authenticated request to each endpoint from the origin https://iampopye.github.io and reading the response headers, on 2 August 2026. Providers change these policies; re-check before you rely on it.

Direct browser access, verified by observed Access-Control-Allow-Origin response headers.
Provider Callable from a browser What was observed
Anthropic Yes An authenticated POST /v1/messages returns Access-Control-Allow-Origin: *. Anthropic requires the opt-in header anthropic-dangerous-direct-browser-access: true, which this demo sends.
Groq Yes An authenticated POST /openai/v1/chat/completions returns Access-Control-Allow-Origin: *.
OpenRouter Yes An authenticated POST /api/v1/chat/completions returns Access-Control-Allow-Origin: *.
OpenAI No The preflight passes, but the actual POST /v1/chat/completions returns no Access-Control-Allow-Origin header whenever an Authorization header is present, so the browser discards the response. Reproduced three times. Removing the key restores the header — that is, OpenAI permits the browser call only when it cannot succeed.
OpenAI-compatible
(Ollama, vLLM, LM Studio…)		 Your call You own the CORS policy on your own server. Ollama, for example, needs OLLAMA_ORIGINS set before a browser page may reach it.

The OpenAI row is the honest argument for self-hosting. A server has no CORS policy imposed on it. The limitation above is a limitation of demos in web pages, not of self-hosted software: an app running on your own machine can call every one of these providers, OpenAI included.

What is in the code today

Read from the default branch at commit 2b93dc1 on 2 August 2026. Every line below was checked against the source rather than the documentation. The project is young; the second column is the part that is not finished.

Shipped and working

  • Provider-agnostic model layer. Anthropic, OpenAI, Groq, OpenRouter, any OpenAI-compatible endpoint, or the Vercel AI Gateway. A provider turns on when its environment variables are present — no rebuild, nothing baked in at build time.
  • Runtime model discovery. The app asks each configured provider what it can serve and caches the answer for a few minutes, falling back to a small seed list if discovery fails, so the picker is never empty and never stale.
  • Streaming chat, with resumable streams if a stream is interrupted
  • History, messages and votes persisted in PostgreSQL via Drizzle ORM, migrations included
  • Artifacts: rich-text documents, code, and spreadsheets, with version history and a diff view
  • A code editor whose Python snippets execute in the browser through Pyodide
  • Auth.js accounts — email and password — plus one-click guest sessions
  • Per-chat public or private visibility
  • Model tools: create document, update document, request suggestions, fetch weather
  • Optional Redis-backed per-IP rate limiting
  • File attachments on messages — the upload route stores them in Vercel Blob, so a token for it is needed

Not done yet — do not plan around these

  • There is no docker compose stack. No Dockerfile and no compose file exist in the repository. Deployment today means running Node yourself against a PostgreSQL you provide.
  • Uploads still require Vercel Blob. The upload route calls @vercel/blob, so file attachments need a Blob token. A local-filesystem driver is not written.
  • .env.example is still the upstream Vercel one. It does not yet list the provider variables the new model layer reads. The README documents them; the example file has not caught up.
  • The Python code artifact loads Pyodide from a public CDN, so that one feature is not air-gap-clean even when your model is local.

Publishing that second column costs nothing and buys the only thing an early project actually needs, which is being believed. If you are evaluating this today, evaluate the first column.

Run it yourself

Node 20 or newer, pnpm, and a PostgreSQL database you control. There is no container image yet — see the status section. 

git clone https://github.com/iampopye/chatbot.git
cd chatbot
pnpm install

cp .env.example .env
# AUTH_SECRET   — openssl rand -base64 32
# POSTGRES_URL  — your own database
# ...and at least one provider variable from the table below

pnpm db:migrate
pnpm dev

The app comes up on http://localhost:3000.

Turning on a provider

Set the variable, restart, and that provider appears in the model picker. Set several and you can switch between them per chat. These names are read straight from lib/ai/config.ts.

One of these is enough to get the app talking to a model.
ProviderEnable withNotes
AnthropicANTHROPIC_API_KEY
OpenAIOPENAI_API_KEYWorks fine server-side. Only the in-page demo above is blocked, and that is a browser rule.
GroqGROQ_API_KEY
OpenRouterOPENROUTER_API_KEYSeveral hundred models behind one key.
Anything OpenAI-compatibleOPENAI_COMPATIBLE_BASE_URLOllama, vLLM, LM Studio, llama.cpp, LiteLLM. Add OPENAI_COMPATIBLE_API_KEY only if your server wants one. With a local server, no request leaves your machine.
Vercel AI GatewayAI_GATEWAY_API_KEYThe upstream template's default, kept as an option.

Models are addressed as provider:model, split on the first colon — anthropic:claude-sonnet-4-5, openrouter:anthropic/claude-sonnet-4.5, compatible:llama3.1:8b. Pick the startup default with DEFAULT_CHAT_MODEL, or replace the discovered catalogue outright with AI_MODELS. Note that .env.example has not yet been updated with these variables — the README is the accurate reference until it is.

Self-hosting advice that applies from day one: generate a strong AUTH_SECRET, never commit .env, terminate TLS in front of the app, and do not expose PostgreSQL to the public internet.

Found a security problem? Please report it privately — the process is in SECURITY.md. Do not open a public issue for a security bug.
